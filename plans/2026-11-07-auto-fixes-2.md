## 1. Summary

Three fixes to the diorama render. Task 220 is the most important. A rung bell swings for one 50 ms tick
and then stops dead, because the server sends `state: "on"` only on the tick the rope is pulled
(`gear.ts:110`, and `step.ts:480` clears events every step). Meanwhile `drawBell` cuts the swing to zero as
soon as `rung` is false (`signals.ts:46-55`). The same gate hides the reduced-motion tilt, because
`motionT` returns `undefined` under reduced motion (`fx.ts:94`). The fix is to let the bell's 1.2 s fx
drive the motion instead of the one-tick state.

Task 221 restores the painter order for a door's opening. `drawScene` puts every `f.door` effect in
`doorFx` (`index.ts:389-391`) and draws them after the row loop (`index.ts:515`). For 450 ms, a door's
sinking leaves are then painted over every figure and wall front further south. ADR 0025 FR5 asks only
that the ring is drawn wherever the door is, out of sight and out of the light too. It does not ask for
the ring to be painted last.

Task 222 makes decor the same on every screen in a room. `decorFor` draws every roll from one
`mulberry32` stream in reading order (`decor.ts:176`, `:197-201`). Any eligible cell gained or lost moves
every later item. A sighted seat's view masks the night zone to `" "`, and `" "` is in `NEAR`
(`decor.ts:134`). A spectator's view does not mask it, and a reload after a cache opens sends different
tiles again. So in room 08 a player, a spectator and a player who reloads each see different walls.

When this was drafted I re-read the code each finding names. It matches the verifier's description:

- `drawBell`'s `!rung` gate and `motionT`'s reduced-motion `undefined`;
- the `doorFx` bucket and its draw after the loop;
- `NEAR` with `" "`, and the single seeded stream.

I did NOT re-read these, and they are the verifier's word only: the server side of the bell (`gear.ts`,
`step.ts`, `perception.ts`) and the per-seat masking in `perception.ts`. Each task therefore begins by
reproducing its finding in a test. A finding that will not reproduce is not fixed; it goes to
`specs/backlog.md` as a dated line. Each task starts with a test that fails on today's code (CLAUDE.md: a
bug fix starts with a failing test). That test is shown red by breaking the guarded code on purpose, then
the fix follows. No test is weakened or deleted.
